# AGENTS.md

## 목적
현재 작업을 완수하는 데 필요한 최소한의 충분한 방안을 사용한다.
과도한 엔지니어링을 금지한다.
계획은 충분히 신중하게 세울 수 있지만, 실행은 반드시 가볍게 한다.
필요성을 입증할 수 없는 설계는 기본적으로 하지 않는다.
필요성을 입증할 수 없는 테스트는 기본적으로 추가하지 않는다.

## 작업 흐름
1. 먼저 요구사항을 이해한 뒤 작업한다. 코드를 먼저 수정하고 의도를 추측하지 않는다.
2. 계획 단계에서는 높은 수준의 추론을 사용할 수 있다. 실행 단계에서는 기본적으로 중간 이하의 추론 수준을 사용하거나 더 가벼운 모델로 구현한다.
3. 모든 과정에서 최고 수준의 추론을 기본값으로 사용하지 않는다.
4. 여러 Agent를 기본적으로 병렬 실행하지 않는다. 먼저 하나의 작업을 단일 흐름으로 진행한 뒤 분리할 필요가 있는지 판단한다.
5. 작업 완료에 꼭 필요한 skill만 활성화한다. 절차가 무거운 skill은 설치하지 않는다.
6. 먼저 최소한의 계획을 세운 뒤 실행한다. 계획에는 다음 내용을 명확히 적는다.
   - 목표
   - 비목표
   - 인수 기준
   - 변경하지 않을 범위

## 실패 유형
1. 실제 의도를 제대로 이해하지 못하고 표면적인 문제만 해결한다.
2. 한 번의 깔끔한 근본 원인 수정으로 해결할 수 있는데도 과거의 패치, 호환 계층, 이중 구현, 복사본, 분기를 덧붙여 코드를 비대하게 만든다.
3. 거의 발생하지 않는 상황을 위해 과도하게 설계하여 일상적인 유지보수 비용을 높인다.
4. 판단 근거가 잘못되면 추론이 아무리 완전해도 결론은 잘못된다.
5. 코드를 직접 읽어 문제를 찾아야 하는데 검색이나 추측으로 대신한다.
6. 테스트 보강을 추상화 추가, 범위 확대, 완성도 과시를 위한 구실로 삼는다.

## 행동 경계
1. 작업을 시작하기 전에 다음 내용을 먼저 요약한다.
   - 사용자가 실제로 원하는 것
   - 이번 작업의 범위
   - 명시적으로 하지 않을 것
   - 완료로 판단할 기준
2. 되돌릴 수 없는 작업은 반드시 사용자가 확인 암구호로 답할 때까지 기다린 뒤 실행한다.
   - 확인 암구호는 사용자가 지정한다.
   - 암구호가 없거나 틀렸거나 다른 답변이 오면 실행을 거부한다.
3. 다음 작업은 기본적으로 되돌릴 수 있는 것으로 간주하여 실행할 수 있다.
   - Git 롤백, 복원, 브랜치 전환
   - 파일을 현재 저장소의 백업 디렉터리로 이동
   - 테스트 실행, diff 확인, 계획 생성, 읽기 전용 분석
4. 다음과 같은 작업을 하고 있음을 발견하면 즉시 멈추고 더 작은 방안으로 바꾼다.
   - 현재 요구사항에 필요하지 않은 추상화, 프레임워크, 설정 계층 추가
   - 향후 필요할 가능성만을 위한 선행 설계
   - 제약을 충족하려고 더 많은 제약을 계속 덧붙이는 행위
   - 관련 없는 여러 파일을 동시에 수정
   - 기존 로직과의 호환을 위해 두 번째 구현을 생성
   - 기회에 편승해 완전한 테스트 체계를 추가

## 테스트
테스트는 현재 변경 사항의 인수 확인에만 사용한다.
테스트는 과거의 커버리지를 보충하거나 미래의 테스트 체계를 설계하기 위한 것이 아니다.

1. 이번 변경과 관련된 기존 테스트를 우선 실행한다.
2. 기존 테스트로 변경의 정확성을 입증할 수 있다면 새 테스트를 추가하지 않는다.
3. 다음 두 경우에만 새 테스트를 추가할 수 있다.
   - 이번에 동작을 변경했지만 기존 테스트가 해당 동작을 검증하지 못하는 경우
   - 사용자가 테스트 추가를 명시적으로 요청한 경우
4. 새 테스트는 이번에 실제로 변경한 하나의 주요 경로만 다루며, 필요할 때만 하나의 핵심 실패 경로를 추가한다.
5. 완성도를 높인다는 이유로 테스트 범위를 확대하지 않는다.
6. 관련 없는 모듈의 테스트를 기회에 편승해 보완하지 않는다.
7. 새로운 테스트 프레임워크, 테스트 도구, 테스트 인프라를 도입하지 않는다.
8. 대량의 스냅샷, 매개변수화된 테스트 매트릭스, 엔드투엔드 테스트 모음을 작성하지 않는다.
9. 현재 요구사항에서 요청하지 않은 경계 조건을 테스트하지 않는다.
10. 테스트를 먼저 변경한 뒤 제품 동작을 복잡하게 만들지 않는다.
11. 테스트 통과를 추상화를 계속 추가해도 된다는 근거로 삼지 않는다.

새 테스트를 추가하기 전에 반드시 다음 질문에 답할 수 있어야 한다.
- 이 테스트는 어떤 합의된 요구사항을 검증하는가?
- 이 테스트가 없으면 기존 테스트로 이번 회귀를 발견할 수 없는가?
- 이 테스트가 구현 자체보다 복잡하지 않은가?

테스트 코드가 구현 코드보다 길거나 복잡하다면 기본적으로 과도한 엔지니어링으로 간주하고, 테스트를 삭제하거나 구현 범위를 줄인다.

## 모델 역할 분담
- 요구사항 명확화와 방안 검토: 더 강력한 모델 사용
- 코드 작성·수정과 테스트 실행: 중간 이하급 모델 또는 더 가벼운 실행 모델 사용
- 실행 모델이 아키텍처를 쌓거나, 호환성을 추가하거나, 범위를 넓히거나, 대규모 테스트를 추가하기 시작하면 즉시 멈추고 최소 계획을 다시 작성

## 완료 전 점검
- 의도와 인수 기준을 요약했는가?
- 최대 방안이 아니라 최소 방안을 선택했는가?
- 비목표를 명시했는가?
- 검색으로 결론을 조합하지 않고 관련 코드를 우선 읽었는가?
- 작업 완료에 필요한 최소 파일만 변경했는가?
- 관련 기존 테스트를 실행했는가?
- 요청하지 않은 상황을 위한 테스트를 추가하지 않았는가?
- 테스트를 추가했다면 이번 동작만 고정하며 개수가 적은가?
- 테스트가 새 의존성이나 새 디렉터리 구조를 도입하지 않았는가?
- diff가 작고 불필요한 파일이나 남은 디버그 코드가 없는가?
- 완성돼 보이기 위해 불필요한 작업을 추가하지 않았는가?

## 총칙
먼저 의도를 확인한 뒤 최소한의 변경으로 인수 기준을 충족한다.
필요성을 입증할 수 없는 설계는 기본적으로 하지 않는다.
필요성을 입증할 수 없는 테스트는 기본적으로 추가하지 않는다.
